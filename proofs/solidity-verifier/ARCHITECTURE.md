# Solidity PLONK Verifier — Architecture

This crate is a **Solidity port of the `midnight-proofs` PLONK verifier**,
specialized for the `zk_stdlib/examples/poseidon` circuit. It runs on the
Prague-era EVM and uses the EIP-2537 BLS12-381 precompiles for elliptic-curve
arithmetic and pairings.

The port is *algebraic*: it is not a pre-computed SNARK wrapper, it is a
reproduction of the full Rust verifier pipeline — Fiat–Shamir transcript,
identity evaluation, linearization, multi-point opening reduction and pairing
check — written in Solidity. Every intermediate step emits a trace event so
that the Rust side can cross-check the two execution paths byte-for-byte.

```
┌────────────────────────────────────────────────────────────────┐
│           proofs/solidity-verifier/ (this crate)               │
│                                                                │

│   │  Rust VK      │ ─────────────► │ PoseidonVerifyingKey.sol ││
│   │  (live)       │                │  (constants-only blob)   ││
│   └───────────────┘                └──────────────────────────┘│
│          │                                     ▲               │
│          │ proof + instance                    │ extcodecopy   │
│          ▼                                     │               │
```

## 2. Two-contract design

### 2.1 `PoseidonVerifyingKey.sol`

A **minimal constants-only contract** whose constructor returns a single
packed byte blob via `RETURN(offset, length)`. After deployment, the blob
*is* the runtime bytecode; the verifier reads it via `extcodecopy`. This
keeps the source file a few hundred bytes regardless of circuit size, and
removes any structural coupling between the two contracts.

The blob is produced by `codegen::render_verifying_key(&VkInfo)` and its
layout is fixed. Sections in order (all big-endian):

| Offset | Size | Field |
|--------|------|-------|
| 0      | 32   | `transcript_repr` (Blake2b VK digest, padded to Fq) |
| 32     | 32   | `ω` (domain generator) |
| 64     | 32   | `const1`: `n`, `k`, advice/fixed/instance cols, challenges, phases |
| 96     | 32   | `const2`: `cs_degree`, simple selectors, blinding, query counts, lookups, trashcans |
| 128    | 32   | `const3`: perm cols/chunks, quotient limbs, total lookup helpers, **num_committed_instance_evals** |
| 160    | 128·F | fixed column commitments (EIP-2537 uncompressed G1) |
| …      | 128·P | permutation commitments |
| …      | 256  | `s·G2` |
| …      | 256  | `-G2` |
| …      |      | Gate bytecode section: selector table + per-poly RPN |
| …      |      | Permutation metadata: chunk_len + per-column (kind, query_idx) |
| …      |      | Lookup bytecode (selector/table/chunks, RPN) |
| …      |      | Trashcan bytecode (selector/constraints, RPN) |
| …      |      | Query schedule: distinct rotations + per-query rotation/col idx |

`codegen.rs::VkInfo::from_live(vk, srs)` walks a live `midnight-proofs`
`VerifyingKey` and builds this struct, serializing every gate/lookup/trashcan
expression to a compact RPN bytecode (see `expr_bytecode.rs`). The bytecode
is interpreted on-chain by `PoseidonVerifier._evalBytecode`, eliminating the
need to emit 10k+ lines of generated Solidity.

### 2.2 `PoseidonVerifier.sol`

The verifier itself. Constructor takes the address of the deployed
`PoseidonVerifyingKey` and caches it as an immutable.

Public entry point:

```solidity
function verify(bytes32 instance, bytes calldata proof) external returns (bool);
```

Internal flow mirrors `proofs/src/plonk/verifier.rs` line-for-line:

```
Phase 0. _loadVk()                      : extcodecopy + header parse
Phase 1. hash transcript_repr + instances
Phase 2. read advice commitments, squeeze (θ)
Phase 3. read lookup multiplicities, squeeze (β, γ)
Phase 4. read permutation-product commitments
Phase 5. read lookup helpers + accumulators
Phase 6. squeeze (trash_challenge), read trashcans
Phase 7. squeeze (y), read quotient-limb commitments
Phase 8. squeeze (x)
Phase 9. read all evaluation scalars in Rust iterator order
Phase A1. _computeLagrangeAux → (l_0, l_last, l_blind)
Phase A2. _partiallyEvaluateIdentities → (selectors, scalars) over 22 exprs
          - gates: interpret RPN bytecode per gate poly
          - permutation: _permExpressions (1 + 1 + (k−1) boundary + k per-chunk)
          - lookup: _lookupExpressions (compression + log-up constraint)
          - trashcan: _trashExpressions
Phase A3. _computeLinearizationCommitment → identities_points, identities_scalars, expectedEval
Phase C.  squeeze (x1, x2), read f_com, squeeze (x3), read q_evals_on_x3, squeeze (x4), read π
Phase D.  _driveMultiPrepare → v, commScalars, fComScalar, piScalar, gScalar
Phase E.  final right-MSM over (≤50 terms) + pairing check
          e(π, s·G2) · e(C − v·G + x3·π, −G2) == 1
```

Every phase is bracketed by `PhaseGas(name, gasUsed)` events so `forge test`
surfaces per-phase gas costs automatically. Every transcript operation emits
one of `TraceChallenge`, `TraceReadScalar`, `TraceReadPoint`, or
`TracePairing`, and algebraic intermediates emit `TraceIntermediate(tag, v)`.
These events are consumed by the Rust harness to cross-check equivalence.

#### Key on-chain primitives

| Component | Precompile | Notes |
|-----------|-----------|-------|
| `keccak256`           | built-in  | one-shot: cumulative-buffer transcript |
| `_fromUniformBytesLE` | `ModExp(0x05)` | 64-byte uniform reduction mod Fr |
| `_frPow` / `_frInv`   | `ModExp(0x05)` | Fr exponent / inversion |
| `_modExpFp`           | `ModExp(0x05)` | Fp arithmetic for G1 decompression |
| `_g1Add`              | `G1ADD (0x0b)` | 256→128 bytes |
| `_g1MsmBatch`         | `G1MSM (0x0c)` | batched MSM (up to 50 terms) |
| `_pairingCheck`       | `PAIRING (0x0f)` | 2-pair check → 0x00/0x01 |

G1 points travel in **compressed** form on the proof wire (48 bytes, zcash
encoding), get decompressed once to the **EIP-2537 uncompressed** form
(`pad16‖x‖pad16‖y`, 128 bytes) and are then re-used by the precompiles.
Decompression is `y = (x³+4)^((p+1)/4) mod p`, with the `sort` bit used to
pick the representative. This is implemented purely in Solidity via ModExp.

## 3. How the two traces meet

Algebraic equivalence is enforced at three granularity levels:

1. **Unit tests** (`test_perm_expressions`, `test_lookup_expressions`,
   `test_trash_expressions`, `test_linearization_commitment`,
   `test_intermediate_sets`, `test_x1_evals_fold`, `test_feval_fold`,
   `test_x4_outer_fold`, `test_pairing_rhs`, …) feed a Rust-computed
   fixture into the matching Solidity helper and diff the result.

2. **Positional signatures** (`test_*_signature`) fold every intermediate
   into `Σ (i+1)·value_i mod Fr` so that a single 32-byte equality check
   covers thousands of values. The Rust side replicates the exact
   Solidity-side loop and the Solidity side recomputes the signature
   inside `verify()`.

3. **End-to-end verify** (`test_verify_poseidon_proof`) runs the full
   flow and asserts `verify()` returns `true` for the Rust-produced
   proof. A companion test (`test_verify_rejects_mutated_proof`) flips
   a byte in the proof and asserts rejection.

4. **Trace-diff harness** (`tests/forge.rs::rust_and_solidity_traces_match`):
   regenerates the proof, runs `forge test`, replays the Fiat–Shamir
   sequence in Rust while emitting the same `TraceEntry` schema, then
   requires the two traces to be element-wise identical across all
   challenges, scalar reads and point reads.

## 4. Non-uniform handling of instance columns

The poseidon example has two instance columns. `zk_stdlib::verify`
always commits to **exactly one** instance column (defaulting to the
identity point when no actual committed instance is supplied) and passes
any public values through the other column.

In the verifier:

* **Committed instance column (col 0)** — the prover provides an eval
  that the verifier reads from the transcript.
* **Non-committed instance column (col 1)** — the verifier computes the
  eval locally as `Σ_i instance_i · L_i(x)`, which collapses to
  `instance · l_0` in the one-public-input case.

`_buildPartialEvalEnv` honors this split via:

```solidity
for (uint256 i = 0; i < vk.numInstanceQueries; i++) {
    if (i < vk.numCommittedInstanceEvals) {
        inst[i] = ea.committedInstanceEvals[i];  // transcript-read
    } else {
        inst[i] = _frMul(pin.instance, e.l0);    // Lagrange
    }
}
```

This mirrors the Rust iterator in `proofs/src/plonk/verifier.rs:252`
which branches on `column.index() < nb_committed_instances`.

## 5. Build, test, bench — command reference

All commands below assume `SRS_DIR` points at the downloaded Filecoin
trusted setup files used by `zk_stdlib` (≈1 GB of `phase1radix2m*`).
If the env var is unset the tests automatically use a pre-bundled test
SRS, but the `generate` binary needs the real one.

```bash
# From the repo root.
export SRS_DIR=$PWD/zk_stdlib/examples/assets
```

### 5.1 Regenerate VK contract + fixtures

```bash
cargo run -p midnight-solidity-verifier --bin generate
```

Produces:
* `contracts/PoseidonVerifyingKey.sol` — new VK blob
* `fixtures/proof.bin`, `fixtures/instance.be`
* `fixtures/vk.bin`, `fixtures/*_fixture.bin` — all per-phase witnesses

Environment variables (optional):
* `POSEIDON_K` — log2 of the domain size (default 6)
* `POSEIDON_SEED` — prover RNG seed (default 1)

### 5.2 Compile the Solidity contracts

```bash
cd proofs/solidity-verifier
forge build
```

### 5.3 Run the forge test suite

```bash
cd proofs/solidity-verifier
forge test
```

Run a single test verbosely:

```bash
forge test --match-test test_verify_poseidon_proof -vvv
```

The full suite currently contains **24 tests**, all passing.

### 5.4 Gas benchmarks

```bash
cd proofs/solidity-verifier
forge test --gas-report
```

`verify()` is already instrumented with per-phase `PhaseGas` events;
`test_verify_poseidon_proof` prints them under `  . <phase>` lines when
run with `-vv`. Total verification gas is reported as `verify() total`.

### 5.5 Rust ↔ Solidity trace-diff end-to-end test

```bash
SRS_DIR=$PWD/zk_stdlib/examples/assets \
    cargo test -p midnight-solidity-verifier --test forge
```

This harness regenerates the VK + proof, runs `forge test -vv`,
replays the Fiat–Shamir sequence in Rust and asserts the two traces
are identical.

### 5.6 CI-friendly one-liner

```bash
SRS_DIR=$PWD/zk_stdlib/examples/assets \
    cargo run --quiet -p midnight-solidity-verifier --bin generate && \
    cd proofs/solidity-verifier && \
    forge build && \
    forge test
```

## 6. Extending to other circuits

The current code is specialised to the poseidon example in two places:

* `src/poseidon_fixture.rs` hard-codes the circuit builder and proof
  construction. A new circuit needs a new fixture module following the
  same trait surface.
* `PoseidonVerifier.sol` is regenerated by `codegen.rs`, which bakes
  the blob layout but keeps Solidity *logic* circuit-agnostic (it is
  driven entirely by the VK blob + RPN bytecode). Moving to another
  `midnight-proofs` circuit should require only:
  1. swap in a new `PoseidonFixture`-equivalent,
  2. re-run `cargo run --bin generate`,
  3. re-run `forge test` — every circuit-specific value is read from
     the VK blob or the RPN bytecode at runtime.

The two circuit-specific assumptions currently encoded in
`PoseidonVerifier.sol` are:

* **Single public scalar instance** (`_buildPartialEvalEnv` collapses
  Lagrange-basis instance evals to `instance · l_0`).
* **One committed instance column** (zk_stdlib default).

Both are mechanical to generalise if/when a non-poseidon fixture is
introduced.
